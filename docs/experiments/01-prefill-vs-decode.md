# Experiment 01: prefill vs decode, sequential vs concurrent

Two questions about serving one small model through the InferLab gateway:

1. **Prompt length sweep.** How do prefill (processing the prompt) and decode (generating tokens) each respond to a longer prompt?
2. **Sequential vs concurrent.** Does sending more requests at once increase throughput, and what does it cost in latency?

## Setup

| | |
|---|---|
| Model | `qwen2.5:3b` via Ollama 0.40.16 |
| Hardware | Apple M5, 16 GB RAM, one machine running gateway, Ollama and the load generator |
| Path | `cmd/bench` → InferLab gateway (`:8080`) → Ollama, all on localhost |
| Mode | streaming (SSE), so TTFT and TPOT are both measured |
| Output length | fixed at `max_tokens: 64`; every request produced exactly 64 chunks |
| Prompts | deterministic filler words after a short instruction, generated by `GeneratePrompt` |
| Prefix cache | defeated: each request starts with a unique `[run N]` nonce, so Ollama cannot reuse a cached prompt prefix |
| Warm-up | one untimed request before each suite, so model load is excluded |

Configs: [`benchmarks/prefill-vs-decode.json`](../../benchmarks/prefill-vs-decode.json) and [`benchmarks/sequential-vs-concurrent.json`](../../benchmarks/sequential-vs-concurrent.json). Reproduce with:

```sh
go run ./cmd/server &
go run ./cmd/bench --config benchmarks/prefill-vs-decode.json
go run ./cmd/bench --config benchmarks/sequential-vs-concurrent.json
```

Raw per-request samples are in [`benchmarks/results/prefill-vs-decode/`](../../benchmarks/results/prefill-vs-decode) and [`benchmarks/results/sequential-vs-concurrent/`](../../benchmarks/results/sequential-vs-concurrent).

## 1. Prompt length sweep

Concurrency 1, 8 requests per point. "Prompt tokens" is Ollama's `prompt_eval_count` for the same prompt text (measured once, via `/api/generate`); the chat template adds a few more tokens per request.

| Prompt words | Prompt tokens | TTFT P50 (ms) | TTFT P95 (ms) | TPOT P50 (ms) | TPOT P95 (ms) | Latency P50 (ms) | Latency P95 (ms) | req/s | tok/s |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 25 | 86 | 89 | 93 | 18.7 | 21.1 | 1264 | 1418 | 0.77 | 49.0 |
| 250 | 332 | 211 | 222 | 18.8 | 23.0 | 1395 | 1665 | 0.70 | 44.5 |
| 500 | 615 | 318 | 336 | 20.0 | 26.5 | 1595 | 1993 | 0.61 | 38.8 |
| 1000 | 1165 | 576 | 603 | 19.0 | 22.3 | 1784 | 1967 | 0.56 | 35.5 |
| 1800 | 2033 | 937 | 1037 | 20.1 | 25.8 | 2191 | 2649 | 0.43 | 27.5 |

**Prefill grows with the prompt; decode does not.**

- TTFT rose from 89 ms to 937 ms as the prompt went from 86 to 2033 tokens, close to linear. A straight line through the endpoints gives about 0.44 ms per prompt token (roughly 2,300 tokens/s of prefill) plus about 50 ms of fixed overhead.
- TPOT stayed between 18.7 and 20.1 ms (about 50 tokens/s) while the prompt grew 24×. The spread is within run-to-run noise.
- End-to-end latency rose by 927 ms across the sweep, and TTFT accounts for 848 ms of that. Decoding 64 tokens costs about 1.2 s regardless of prompt size.
- The tok/s column falls with prompt length only because it divides by total time, which includes prefill. It is not a decode slowdown.

## 2. Sequential vs concurrent

Prompt of 250 words (332 tokens), 16 requests per point.

| Concurrency | OK | TTFT P50 (ms) | TTFT P95 (ms) | TPOT P50 (ms) | TPOT P95 (ms) | Latency P50 (ms) | Latency P95 (ms) | req/s | tok/s |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 16/16 | 345 | 418 | 20.8 | 27.4 | 1656 | 2101 | 0.58 | 37.2 |
| 2 | 16/16 | 1635 | 1995 | 24.5 | 30.3 | 3257 | 3694 | 0.62 | 39.6 |
| 4 | 16/16 | 5120 | 5857 | 26.5 | 29.9 | 6773 | 7610 | 0.57 | 36.4 |
| 8 | 16/16 | 12543 | 13961 | 28.0 | 33.8 | 14373 | 15696 | 0.53 | 33.7 |

**More concurrency bought no throughput, only waiting.**

- Throughput stayed flat at 0.53–0.62 req/s from concurrency 1 to 8, so the backend was already saturated by a single stream.
- Latency grew roughly in proportion to concurrency. At concurrency 8, median latency was 14.4 s against 1.7 s sequentially, and almost all of it was time to first token (12.5 s). That matches requests queueing behind each other: each waits for about `concurrency - 1` others at roughly 1.6 s each.
- TPOT rose from 20.8 to 28.0 ms (+35%), so streams that do run share the hardware rather than getting faster. I did not isolate the cause.
- No request failed at any level.

## Caveats

- **Small samples.** 8 requests per sweep point and 16 per concurrency point, on one machine with other processes running. Differences under about 100 ms are not meaningful: the same configuration (250 words, concurrency 1) gave a TTFT P50 of 211 ms in the first suite and 345 ms in the second.
- **Client-side timing.** TTFT includes the gateway hop and localhost networking, not just the model.
- **Token counts** in the `tok/s` columns are SSE content chunks, an approximation of backend tokens. The prompt token counts above come from Ollama directly and were measured once, not per request.
- **Why the backend serialized** was not checked (I did not read Ollama's parallelism setting). The flat throughput is consistent with it handling one request at a time, but the data alone does not prove it.
- **One model, one backend.** Results for larger models, a GPU server, or vLLM with continuous batching may differ sharply, especially the concurrency result.
